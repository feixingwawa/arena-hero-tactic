# Arena Hero 战术 Agent「优化完善」增量 PRD

- 版本：v1.0
- 产出：软件产品经理（software-product-manager）
- 日期：2026-08-07
- 项目：arena_hero_tactic（Arena Hero 战术 agent 优化增量）

## 1. 项目信息

- **Language**: 中文
- **Programming Language**: Python 3.11+ / arena-hero SDK（沿用现有架构）
- **Project Name**: arena_hero_tactic（优化增量）
- **原始需求复述**：
  1. 修复三个 Worker 在距 Core d=36~37 处 RIGHT↔LEFT 反复横跳、不采集、res 卡 2 无法 spawn 的死循环；
  2. 依据官方规则 v0.14 优化资源采集、探索与经济（移除已废弃维护费、使用动态单位价格、利用资源自动补充）；
  3. 整体完善战术（地图记忆、螺旋扫掠、Beacon/回收/分工/Core 迁移等）。

## 2. 问题实证（日志/代码核验）

- `logs/agent.log`：`explore:RIGHT:r=32:d=36` 重复 **29 次**；`explore:LEFT:recall:r=32:d=37` 重复 **29 次**；`recall` 共 **154 次** → Worker 被困 d∈[36,37]。
- 根因链（`economy.py` command_workers）：
  - `recall_dist = explore_max_radius + 4 = 36`（line 499），d≥37 触发回撤一步 → d=36；
  - d=36 不触发 recall，探索强制「绝不朝 Core 收缩」（line 595-605）→ 外扩一步 → d=37；
  - **36↔37 构成势阱死循环**；r_now 封顶 32 后又无新目标，ph/ax 每 tick 翻转加剧抖动。
- `res_vis=0` 共 **704 次**（总 753 行威胁日志中占 93%）→ 视野内几乎无资源；`harvest` 仅 **8 次**、`deposit` 189 次 → 采集严重不足、经济停摆。
- 代码：`config.py` 仍含 `upkeep_soft_cap/hard_cap/population_upkeep`（v0.14 已移除维护费，过时）；`economy.py` 用固定 `worker_cost=5` 等（未用 SDK `rules.unit_cost()` 动态价格）；无地图记忆（仅模块级方向记忆）。

## 3. 产品目标（一句话）

**让 bot 在 v0.14 规则下从「盲目外扩、卡死回撤」转为「有记忆的螺旋扫掠 + 可持续回访采集」的经济正循环，杜绝 d=36/37 横跳，人口可健康突破 20。**

## 4. 用户故事

1. As a bot，我希望 **修复 recall 边界横跳**，以便 Worker 不会在 d=36/37 之间空转，而是持续抵达新区域并发现资源。
2. As a bot，我希望 **记住见过的资源点与障碍**，以便采集后按刷新周期回访、且不重复探索死胡同（地图记忆）。
3. As a bot，我希望 **探索改为螺旋扫掠**，以便低视野（Worker 3 格）下也能按区域覆盖搜索，而不是沿主轴直线外扩撞边界。
4. As a bot，我希望 **使用官方动态单位价格 + 移除维护费逻辑**，以便人口越过 20 后仍能按真实成本理性 spawn，不被过时规则误卡。
5. As a bot，我希望 **优先利用 Beacon 与 cargo 回收**，以便单位获取双倍资源/复活掉落的收益，加速经济。

## 5. 需求池

### P0（必须，阻断性问题）

- **P0-1 修复 recall 边界横跳**
  - 消除 d=36/37 势阱：提高/移除 `recall_dist` 硬边界（建议 `explore_max_radius + 8` 或改为「软回撤」——连续 N tick 无进展才回撤）；探索目标改为「目标点导航」而非「每 tick 外扩一步」。
  - 删除「绝不朝 Core 收缩」对扫掠路径的硬禁止，允许切向扫掠（不靠近 Core 即可），避免单维势阱。
  - 验收：日志中同一 Worker 不再出现 >10 tick 的 d∈[36,37] 交替；探索有前进增量（d 单调外扩或沿环形移动）。
- **P0-2 移除过时维护费逻辑**
  - 删除 `population_upkeep`、`upkeep_soft_cap/hard_cap` 及 `choose_spawn` 中 `upkeep>0` 阻断、`population_upkeep(pop+1)>0` 预测（`economy.py` line 257/274）。
  - `_get_upkeep_next` 不再参与 spawn 决策。
  - 验收：pop≥20 时不再被维护费逻辑阻止 spawn；config 中无 upkeep 字段引用。
- **P0-3 使用 SDK 动态单位价格**
  - `can_afford` 前调用 `arena_hero.rules.unit_cost(unit_type, pop)`（pop 用 spawn 后人口估算），替换固定 `worker_cost/vanguard_cost/ranger_cost`。
  - 保留 `reserve_resources` 应急预留。
  - 验收：单测覆盖 pop 0-19（基础价）与 20/25（`round_half_up(base×(13/10)^k)` 涨价档）下的 cost 计算正确；成本随人口变化可测。

### P1（应该，显著提升）

- **P1-1 地图记忆（资源点/障碍缓存 + 刷新回访）**
  - 新增跨 tick 记忆模块（进程内单局状态）：资源点集合（含已消耗状态）、障碍集合（地形永久）、最近访问 tick。
  - 利用规则「每 4 resolved tick 资源点按 quota=max(2, floor(16*8/(8+ring))) 回补」：对已消耗资源点按 ring 计算刷新节拍，安排 Worker 回访。
  - 障碍进入记忆后用于路径规划（绕障），减少死路重复探测。
  - 验收：同一区域不重复扫描；已消耗资源点在刷新后会被重新分配采集。
- **P1-2 探索改螺旋/环形扫掠**
  - 用确定性螺旋扫掠（按 Worker 索引分扇区、按 ring 半径逐环覆盖）替代当前「主轴外扩 + 相位振荡」。
  - 探索目标为具体 Position，沿曼哈顿路径移动；到目标后推进下一环，而非无目标盲目外扩。
  - 验收：多 Worker 探索覆盖扇区不重叠；无资源时持续前进且不触发 recall 边界。

### P2（可延后，锦上添花）

- **P2-1 Beacon 利用**：识别持有 Beacon 的 Worker，采集收益翻倍（1 点→2 资源），优先派其到资源点而非探索。
- **P2-2 cargo 回收**：检测死亡掉落 cargo，派空载 Worker 前往回收。
- **P2-3 多 Worker 分工**：按象限/环带划分采集与探索区域，避免扎堆同一资源点。
- **P2-4 Core 迁移评估**：按「迁移成本 4 tick/cell」评估 Core 是否应迁向资源富集/安全区域（低优先级，需更多信息）。

## 6. 待确认问题（≤3）

1. **资源补充节拍观测**：SDK Turn 中「4 resolved tick」如何观测（resolved_tick 字段？），`resource_cells` 每 tick 是否仅含当前可见格？——影响回访调度设计与记忆状态机（须区分「已消耗未刷新」与「未见」）。
2. **人口目标重设**：移除维护费后 `max_population`（现 18）与 target 编制是否上调？是否接受 pop≥20 后的动态涨价（例：Worker 20+ 时 7→9 资源），还是维持保守人口？（默认建议：接受涨价、max_pop 调至 ~30，但需与战斗/资源速率平衡）
3. **Beacon/掉落机制细节**：Beacon 在 [0,0] 的拾取方式与持有者判定 API；死亡掉落 cargo 的可见性与拾取 API（`cargo` 掉落在哪些字段暴露）？——决定 P2-1/P2-2 可落地性。
